# NearSend 连接问题复盘

这次问题的核心不是 Rust，也不是单纯的 Flutter 问题，而是 Windows 防火墙、端口占用或保留、程序路径绑定、以及 UI 状态误报叠在一起。

## 现象

- 电脑可以给平板发消息。
- 平板不能给电脑发消息或文件。
- 本机 `127.0.0.1:54317` 可以访问，但平板浏览器访问电脑 IP 超时。
- 临时关闭 Windows 防火墙后，平板可以访问电脑。
- 后续复制 Release 到 `D:\NearSend` 后，原路径能收，D 盘路径不能收。
- 设置页有时显示 TCP、UDP、程序未放行，但实际已经能收到平板请求。

## 根因

Windows 防火墙的入站规则同时受端口和程序路径影响。程序规则绑定的是 exe 的绝对路径：

```text
C:\Users\HP\Desktop\teasend\build\windows\x64\runner\Release\nearsend.exe
D:\NearSend\nearsend.exe
```

这两个路径在 Windows 防火墙看来是不同程序。即使端口已放行，如果当前 exe 路径没有被放行，或者曾经被创建过阻止规则，平板仍然可能访问不到电脑。

另外，Windows 上 `53317-53322` 可能被系统保留或占用，所以服务需要 fallback 到 `54317`、`55317`、`57317` 等端口段。

## 解决方式

### 端口 fallback

接收服务不再只依赖 `53317`，而是支持多个端口段：

```text
53317-53322
54317-54322
55317-55322
57317-57322
```

手动连接也会尝试这些 fallback 端口。

### 一键防火墙修复

一键修复现在会：

- 开启本地防火墙规则。
- 放行 NearSend TCP 入站端口。
- 放行 LocalSend UDP 发现端口。
- 放行当前正在运行的 `nearsend.exe`。
- 同时兼容 Debug 和 Release 路径。
- 清理当前 exe 路径上已有的入站阻止规则。
- 重新创建允许规则。

这解决了“复制到 `D:\NearSend` 后不能收”的问题。

### UI 误报修复

如果电脑已经收到平板请求，例如：

```text
register from 10.241.56.131 POST /api/localsend/v2/register
```

说明真实网络链路已经打通。此时设置页以实际连通状态为准，不再展示误导性的防火墙检测原始输出。

## 结论

真正的根因是 Windows 防火墙按“端口 + 程序绝对路径”拦截入站，而运行路径多次变化。端口 fallback、路径放行和阻止规则清理一起做完后，平板到电脑的消息和文件传输才稳定。
